- ステータス: **論点 Q1〜Q7 は確定（2026-10-15）。窓との多少の重なりは仕様（許容量パラメータ）。実装は含まない**

- 利用ゲーム: sit-by-me（台帳 `docs/monsters.md` 3-7「サイズ区分」。縦横比 1.8 以上=2x1 / 0.55 以下=1x2 / 中間=1x1 の仮置き規則で割り当て済み。ボスは大型で区分は未決）
- 関連: #736（side 戦闘）、#747（奥行き）、#737 / #760 / #848（アクスタ）、#813（味方の枠固定）、#832 系（敵の行動。ビットを先に倒すとボスだけ残る等の意味づけはこちらで、本設計は配置の表現まで）

## 0. 要約

- 今の敵配置（`computeFormation(side='enemy')`）は「体数 N と最大縦横比から、収まる最大の size を逆算する」方式。**N が増えるほど size が縮む**のは構造上の必然で、サイズ区分を入れる余地もない（全員が同じ高さ `size`、幅だけ縦横比で変わる）。
- 設計案は、味方 #813 と同じ作りを敵に適用する。**敵側に「見えないグリッド」（既定 6列×2行）を frontmatter で有効化**し、セルの大きさは**体数に関係なくグリッドだけで決める**。敵はサイズ区分（`1x1` / `2x1` / `1x2` / `2x2`、それ以上も可）ぶんのセルを占有し、絵はその占有領域に contain で収める。
- 群の書式は既存 `[エンカウント群: a, b, a+b]` を**後方互換のまま拡張**する（配置 `@C1`、個数の幅 `*1..2`、群の重み `:3`）。書式の拡張は TS 側（`rollEncounter` 周辺）で解釈でき、parser は群を生文字列のまま透過しているので Rust 変更は不要。Rust 変更が要るのは `サイズ:`・`倍率:`（モンスター定義）と `battle_enemy_grid`（frontmatter）の 2 種で、これは wasm 再ビルド＋pkg コミットが必要。
- #838 は、グリッド有効化と**独立に**現行配置でも起きている。ただし kako-jun 方針（2026-10-15）で「窓と多少かぶったほうが大きくて立体感が出る」ため、**窓との重なりは許容量（既定: 絵の高さの 25%）まで仕様**とし、超える場合だけ直す。2 列で隣の板にかぶるのは不具合として直す。**先に小さな PR（段階 0）で直す**。
- 既定の挙動は不変。`battle_enemy_grid` を書いたゲームだけがグリッド方式になる。

## 1. 現状分析

### 1.1 今の敵配置アルゴリズム（`frontend/src/game/battleLayout.ts`）

`computeSideBattleLayout` が stage（ログ帯と下パネルの間）を求め、味方 (#760/#813) の斜め一列に必要な幅 `partyW` を右端に取り、**残りの左側全部を `enemyRegion` として敵へ渡す**。敵は `computeFormation(enemyRegion, enemyCount, 'enemy', true, …, enemyAspects, { maxSize: 480, minSize: partyHeight })` が決める。

1. 全員の枠は**同じ高さ `size`**、幅は `size × 縦横比`（縦横比は丸め 0.2〜3）。列幅は**最大の縦横比**で揃える（`cellW = size × maxAspect`）。サイズ区分に相当する概念はない。
2. `size` は列数 `columns` ごとに `min(regionW / ((columns + stagger) × maxAspect), regionH / rowCount − ラベル予約, maxSize)` で逆算する。`rowCount = ceil(count / columns)`。
3. 列数は「3 体まで 1 列・4 体以上は 2 列」を下限に、`size ≥ max(SIDE_READABLE_SPRITE_SIZE, 味方の立ち絵の高さ)` に届く最小の列数を選ぶ。届かなければ最大 size の列数。
4. 余った領域は、`originX/originY` で**領域の中央**に寄せて置く（体数で重心も動く）。奇数行は千鳥（右へ `SIDE_STAGGER_RATIO` = 0.25）。
5. 敵ラベル（名前＋HP）を各行の足元に `extra`（隙間 2 + 2 行 30px）ぶん予約する。低い領域ではラベルだけ省く。
6. 縦長 stage（`stage.h > stage.w`）では、敵領域の上端を味方 `party[1]〜[2]` の足元の中ほどまで下げる（下げ幅は stage 高さの 0.4 倍まで）。
7. `BattleScreen.layoutSide` が結果を受け、`placeEntityView` が `computeContainFitRect(tex, slot.width, size)` で絵を枠に収める。アクスタ (#737/#760) のときは**正方形の箱**（`max(size, slot.width)`）を作り、板（`pad` ぶん外へ広がる）・台座・影を重ねる。

### 1.2 体数で縮む理由

手順 2 のとおり、`size` は「領域を体数で割り戻した値」。1 体のときは `min(regionW, regionH − ラベル, 480)` の大きさ、2〜3 体のときは縦に割って縮み、4 体以上は 2 列でさらに縮む。**セルという固定の基準が存在しない**ので、ウニもドラゴンも「領域に収まる最大」で同じ高さになる。寺町実験 (sit-by-me#31) で確認された現象で、味方に #813 を入れたのと同じ構造的な直し方（常に最大セル数ぶんで計算し、空きは描かない）が敵にも要る。

### 1.3 #838 の症状と原因（読解による推定。実装時に実機で確定する）

症状: side + acrylic で 1 体（割れたガラス・氷柱）だと上端がメッセージ窓（ログ帯 = `messageRect`）の下にもぐる。2〜3 体の氷柱・ビール瓶でも上端が隠れる。4 体以上の 2 列で細長い絵が隣にかぶる。

**方針（kako-jun 2026-10-15）**: 「ウインドウと多少かぶったほうが大きくて立体感が出ていい」。窓との重なりは**許容量（既定: 絵の高さの 25%）まで仕様**で、超える場合だけ直す。隣の板へのかぶりは不具合として直す。

原因の推定（読解による。実機で確定する）:

- **窓との重なり（許容量内なら仕様・超えたら直す）**: `computeFormation` は「`size` の枠」を領域内に収めるが、アクスタの板は `pad`（余白＋線ぶん）だけ**枠の外へ広がる**。1 体のとき枠は領域の上端（ログ帯の直下 `SIDE_GAP` 6px）まで届くので、板の上端がログ帯の下にもぐる。ログ帯のパネルは sideStage より手前に描かれる。もぐる量は縦長の絵（`regionH − ラベル` が律速で領域の高さいっぱい使う）で最大だが、`pad` ぶんは絵の高さの 1 割未満が見込みで、**多くは許容量 25% の範囲内（＝仕様どおり）**。症状の報告は、許容量を超えて頭が切れて見えた場合と、`pad` 以外の要因（縦長の箱の上側の余白）があるかを実測で確かめる。
- **2 列で隣にかぶる（直す）**: 列ピッチ `colPitch = cellW = size × maxAspect` は「スプライト枠の幅」基準で、板の `pad`・千鳥のずらし（奇数行が右へ 0.25）を含まない。幅の小さい（細長い）絵は枠自体は隣と離れているが、板が左右へ `pad` ぶん広がって隣の板に重なる。最大縦横比の敵に揃えた列幅のため、細長い敵と横長の敵が混在すると列間隔が不揃いになる。**直し方は列ピッチに `pad` を含める**。
- 奥行き (#747) の縮尺は「元の予約領域の上端・水平中央を保って縮める」ので、上端を押し下げる側に働き、症状を悪化させない（原因ではない）。

### 1.4 エンカウント群

`[エンカウント群: a, b, a+b]`（parser: `inject_encounter_groups_into_last_map` が `Vec<String>` を生のまま保持）。`rollEncounter` が、`rate` で抽選後に `Math.floor(rng() × groups.length)` で**重み均等**に 1 群を選び、`+` で分解して `MonsterDef` から `BattleEntity` を組み立てる。体数・種類は群の文字列で固定。同じ敵を並べるには `a+a+a` と書く。`BattleEntity` にサイズ・配置の情報はない。

### 1.5 台帳側（sit-by-me）

`monsters.md` 3-7 に敵ごとのサイズ区分（縦横比 1.8 / 0.55 の仮置き規則、ボスは大型で区分未決）。エンジンは区分を受け取れる想定。区分の数値を解釈するのは本設計の `サイズ:`。

## 3. 設計案

### 3.1 グリッドの定義

frontmatter に 1 キーを足す（戦闘画面の設定はすべて frontmatter で共有しているため、他の `battle_*` と並べる）。

```yaml
battle_enemy_grid: 6x2
```

- 書式: `列数x行数`（半角 x または ×、大小無視）。**列数 1〜12・行数 1〜4** に丸める。不正値・未指定は無効＝従来方式（R11）。
- 既定の値を黙って決めない。**キーを書いたときだけ有効**で、`on` のような値は不正として無効。「縦2行 × 横6列くらい」は例示の既定値として spec に書くが、有効化は明示する。
- `battle_layout: side` のときだけ効く（`front` では無視）。GUI 専用（TUI は読まない）。
- データの流れは `battle_atb` 等と同じ: parser（`Document`）→ `normalizeDocument` → `rpgProjectFromDoc`（`normalizeEnemyGrid`）→ `fieldBattle.ts` の `readFieldBattleSettings` → `BattleScreen` オプション → `computeSideBattleLayout` 入力。
- **座標系**: 列は画面の左から `A, B, C, …`（左 = 奥・味方から遠い、右 = 手前・味方に近い）。行は上から `1, 2, …`（上 = 奥、下 = 手前＝足元に近い）。`C1` = 左から 3 列目・上の行。表計算のセル名と同じで、群の書式に埋め込んでもカンマ・`+` と衝突しない。

### 3.2 セルの大きさ（体数に依存しない）

`computeSideBattleLayout` が、グリッド有効時は `enemyRegion` から**セル一辺 `cell`** を求める。入力は領域・列数 C・行数 R・ラベル帯だけで、**敵の体数・種類・縦横比は一切入らない**（#813 と同じ）。

```
labelBand = SIDE_LABEL_GAP + SIDE_LABEL_HEIGHT          // 行ごとの足元ラベルの予約
cell      = min( regionW / C,  (regionH - R*labelBand) / (R - ov) )   // 正方形セル（0 以下なら 0）。ov = battle_enemy_window_overlap（窓の下へ延ばす上端ぶん ov*cell を領域に足した閉形式。ov=0 なら regionH/R - labelBand）
gridW     = cell * C,  gridH = (cell + labelBand) * R   // cell = 0（置けないほど狭い）のときはラベル帯も 0 で、グリッド全体が 0
```

- セルを**正方形**にする理由: サイズ区分の縦横比（2x1 = 2:1, 1x2 = 1:2）が台帳の割り当て規則（縦横比 1.8 / 0.55）と一致し、占有領域の contain が直感どおりになる。
- グリッド全体は `enemyRegion` 内に、**横は中央・縦は下端（足元側）**に置く。余りは捨てるので、体数で重心は動かない（現行の「領域の中央に寄せる」はやめる）。縦長 stage の下寄せ (#760) の考え方（領域を下げて味方の頭とぶつけない）は、領域 `enemyRegion` の決め方として**そのまま再利用**する。
- ラベルは行ごとに足元へ置く。占有が複数行の敵のラベルは**占有領域の最下行の足元**。行の `labelBand` はセルの外側（下）に取るので、行内の絵はセル全体を使える。ラベルが読めない幅（`isLabelWidthReadable`）の敵はラベルだけ省く（現行ルールを流用）。
- 狭い画面（縦持ちスマホ）では `regionW / C` が小さくなり `cell` が小さくなる（例: 360px 幅・味方 100px 確保で 230px ÷ 6 ≒ 38px）。これは #813 の味方と同じく**仕様として小さくなる**（体数ではなく画面で決まる）。作者が狭い画面を主対象にするなら `4x2` 等を選ぶ。→ 確定 Q2。

### 3.3 サイズ区分（モンスター定義）

```markdown
[モンスター wallstain]
名前: 壁の染み
サイズ: 1x2
倍率: 1.0
[/モンスター]
```

| キー | 別名 | 既定 | 説明 |
|---|---|---|---|
| `サイズ` | `size` | `1x1` | 占有するセルの 幅x高さ（整数 1 以上。上限はグリッドの列数・行数。`2x1` = 横2倍、`1x2` = 縦2倍、`3x2` のようにそれ以上も可）。大小・全角× 可。不正値は警告して 1x1 |
| `倍率` | `scale` | `1` | 占有領域の中での**表示倍率**（0.25〜1。下の「倍率」を参照）。サイズ区分の「枠」はそのまま、絵だけ縮める |

- 区分は `MonsterDef.size`（`{w, h}`）と `MonsterDef.scale` に載せ、`rollEncounter` が `BattleEntity`（`layout?: { w, h, scale, cell? }`）へ写す。`サイズ:` を書かない敵は `layout` なし＝1x1・倍率 1。**エンジン（`battleEngine.ts`）は読まない**（描画専用のマスターデータ。ADR 0002 のとおり GameState に中間状態を足さない）。
- **倍率**: 「実際の大きさの違いが画面に出る」ためにはセル（サイズ区分）で大小を表すのが主、`倍率` は同じ区分の中の微調整（例: 同じ 1x1 の中で小さめの敵）。`1` を超える倍率は、占有領域を超えて隣や窓にはみ出す＝不変条件を壊すため**受け付けない（上限 1）**。大きく見せたいときは区分を上げる。→ 確定 Q3。
- **占有領域**: 左上セル `(c, r)` から `w × h` セル。矩形は `x = gridX + c·cell`, `幅 = w·cell`, `高さ = h·cell`（ラベル帯は最下行の下）。複数行の敵は、行の間のラベル帯ぶんを含めず、**最下行のセルの下端に揃えて**高さ `h·cell` を取る（同じ行の 1x1 と足元・`floor` が合い、2x2 は 1x1 の幅・高さとも厳密に 2 倍になる）。
- **ボス**: 台帳の方針（すべて大型）はサイズ区分で表す。エンジンに「ボスかどうか」の概念は足さない。

### 3.4 群の書式の拡張（後方互換）

群は引き続き `[エンカウント群: g1, g2, …]` のカンマ区切り。**群の中の各項は `+` 連結**。ここまで既存と同じ。各項（敵）と群全体に、**任意の修飾子**を足す。ids は slug（`@` `*` `:` `.` を含まない）なので、既存の群は 1 文字も変えずに同じ意味で解釈される。

| 修飾 | 書式 | 意味 |
|---|---|---|
| 配置 | `id@C1` | その敵の左上セルを列 C・行 1 に固定（R6）。列は `A`〜、行は `1`〜 |
| 個数（固定） | `id*3` | 同じ敵を 3 体（`a+a+a` の短縮） |
| 個数（ランダム） | `id*1..3` | 1〜3 体を一様に選ぶ（R9）。最大数で収まり検証 |
| 群の重み | 群の末尾に `:3` | 抽選の重み（既定 1。整数 1 以上）。**群全体にかかる**ので最後の項の後ろ |

組み合わせ例: `boss@C1+bit@E1+bit@E2:2`（配置つき・重み 2）、`slime*1..3`（スライム 1〜3 体）。

- **ランダム構成（種類）**は、群を複数並べて重みを変えることで表す（種類違いの群を並べるだけ）。体数のランダムは `*m..n`。両方を混ぜる群（`a*1..2+b*0..1`）も書ける（`*0..n` で 0 体を許すが、群全体が 0 体になったら 1 回振り直す）。
- **抽選の互換**: 重みの指定が**どの群にも無い**ときは、現行の `Math.floor(rng() × groups.length)` をそのまま使う（乱数の消費も同じ。既存のテスト・再現と同じ結果）。重みがあるときは、累積重みから 1 回の `rng()` で選ぶ。`*m..n` は、群を選んだ後に範囲ごとに 1 回ずつ `rng()` を消費する（範囲指定を書いた群だけ追加消費）。
- **配置の解釈単位**: 群の配置は群の文字列の中に閉じる（敵の定義側に「いつもここ」を持たせない。同じ敵でも群によって位置が違うことがあるため）。配置の同じ敵が複数体いるとき（`bit*2@E1`）は、`@` を**最初の 1 体**の位置とし、残りは自動配置（3.5）。
- **parser**: 群は `Vec<String>` の生文字列透過のままなので Rust 変更は不要。解釈は TS 側の新しい純粋関数（案: `frontend/src/game/enemyGroup.ts` の `parseEncounterGroup`）が持つ。構文エラーの項は警告して**その項だけ捨てる**（現行の「未知の id は警告して飛ばす」と同じ寛容さ）。
- **TUI/ほかの利用**: `EventDisplay.tsx` 等が群を表示しているなら生文字列のまま表示で問題ない（構文を解釈しない）ことを実装時に確認する。

### 3.5 自動配置の順序と、収まらない群

配置は純粋関数（案: `enemyGrid.ts` の `placeEnemies(grid, items)`）。入力は敵の `(w, h, 配置?)` の並び、出力は各敵の `(col, row)`、または収まらない敵のリスト。

1. **配置指定つきを先に確定**: 群に書かれた順に、指定セルに置く。範囲外・他の占有と重なるなら**エラー**。
2. **残りを書いた順に自動配置**: グリッドを「**手前の列から奥へ**（右の列 → 左の列）、各列は上の行 → 下の行」の順に走査し、その敵の占有矩形が全部空いている最初の位置に置く（first-fit）。
   - 手前の列から埋める理由: 味方に近い側に敵が寄り、体数が少なくても 1 体目の位置が体数によらず同じ（R3）。左から埋めると、少数のとき敵が味方から遠い左端に寄る。→ 確定 Q4。
   - 走査の基点は占有矩形の左上セル。幅 w の敵は、列 `C − w`（右端に収まる最も手前）から始める。
3. 置けない敵が 1 体でも出たら、その群は**収まらない群**。

**収まらない群の扱い**:

- **定義時（ゲーム読み込み時）に検証**する: すべてのマップの全群について、`*m..n` は**最大数**で、実際に配置を試す（`rpgProjectFromDoc` の後段で 1 回）。収まらない群は**エラーとして一覧**し、読み込みはその群を**無効化（抽選候補から外す）**して続行する。ゲームが開けなくなる事態は避け、作者へはコンソールのエラーと（デバッグ表示があれば）画面の警告で知らせる。
- ランタイムの保険: 検証をすり抜けた群（実行時に組み立てた敵など）で置けない敵は、**描かず**警告ログを出す。戦闘そのものは続行する（描かれないだけで HP/行動はある、は望ましくないので、検証側でほぼ防ぐ前提）。→ 確定 Q5（置けない敵を戦闘から除くか）。
- 縦2倍・縦横2倍は全行を使うので同じ列に別の敵は入らない、という要件 R4 は、占有矩形の重なり判定で自然に満たされる（`R = 2` かつ `h = 2`）。

### 3.6 描画

- **contain**: 占有領域（幅 `w·cell`、高さ `h·cell`）に、絵を縦横比維持・**足元中央**で収める（`computeContainFitRect` を流用）。`倍率` は contain した結果をさらに足元中央基準で縮める。`SpriteSlot` は `{x, y, width: w·cell, size: h·cell}` で表し、既存の `placeEntityView` が長方形の枠をすでに扱える（味方 #760/#813 で実績あり）ため、レンダラの変更は小さい。
- **アクスタ (#737/#760/#848)**: 板の `pad`（余白＋線）と台座の厚みは**占有領域の内側に取る**（領域を `pad` ぶん内側へ縮めた矩形に絵・箱を収める）。これで板が隣のセルへはみ出さない（窓との重なりは次項の許容量の範囲で別に扱う）。`pad` は `size` に比例する量なので、「占有領域から `pad` 比を引いた箱」を `computeAcrylicGeometry` の入力枠として渡す形（案）。#838 の「2 列で隣にかぶる」は同じ手当てで根本的に消える。
- **重なり順（R7）**: 各敵の `floor` は「占有領域の下端」。`floor` 昇順（奥 → 手前）に描き、同じ `floor` は**列の昇順（左 = 奥が先）**。行 1 の敵より行 2 の敵が手前に重なる。奥行き (#747) の縮尺は、最前列の `floor` を**グリッドの最下行の下端（体数によらない固定値）**にして求める（味方の 4 枠固定と同じ思想。空きセルがあっても縮尺が変わらない）。
- **メッセージ窓との重なりの許容 (#838・方針変更 2026-10-15)**: 窓は敵の**手前（上）**に描く（現行どおりログ帯のパネルが sideStage より手前）。敵の絵の上端の一部が窓の下に入ってよい。許容量は frontmatter `battle_enemy_window_overlap`（案。0〜0.5 の数値、既定 `0.25`、不正値は既定）で、**各敵の占有領域の高さに対する比**（アクスタの板の `pad` も絵に含めて数え、`pad` が窓の下に入るのも許容量の内）。
  - 根拠: 25% なら頭（上 30%）が完全には隠れず、立体感（敵が窓の奥から迫る）が出る。0 にすれば従来の「隠れない」になる。0.5 を上限にするのは、顔が半分以上隠れる設定を作らせないため。
  - 実現: グリッド領域の上端を `log` の下端 + `SIDE_GAP` から**最大 `overlap × cell`（1x1 の高さの許容量）だけ上へ延ばす**。最上行の 1x1 が許容量ちょうど、2 行以上の敵は高さが大きいぶん比が小さくなるので、全員が許容量以下。セルの大きさの式は 3.2 のとおり（延長ぶんを含めた閉形式）。
  - 窓の外側（log 帯の上や画面外）には出さない: 延長しても `log.y + log.h − overlap × cell ≥ log.y` を満たす範囲に丸める。
- **ラベル**: 占有領域の最下行の直下（現行と同じく sideStage の外の `labelLayer` に絶対座標で）。同じ列の隣の敵のラベルと重ならないよう、ラベル幅は占有幅 `w·cell` まで。
- **死亡・消滅**: 倒れた敵のセルは**詰めない**（現行のスロットも index で固定されている）。空いたセルは何も描かない。

### 3.7 既存方式との共存（R11）

`computeSideBattleLayout` の入力に `enemyGrid?: { cols, rows }` と、敵ごとの `enemyFootprints?: { col, row, w, h, scale }[]` を足す。

- `enemyGrid` なし → 現行の `computeFormation(…, 'enemy', …)` をそのまま呼ぶ（**一切変えない**）。#838 の修正（段階 0）だけがここに入る。
- `enemyGrid` あり → 新関数 `computeEnemyGridLayout(region, grid, footprints, withLabel)` を呼ぶ。出力は同じ `SpriteSlot[]`（`enemies[i]` は `state.enemies` の index 順）なので、`BattleScreen` 以降（ラベル、演出、被ダメ数字の `anchorX/Y`、対象選択の `menuGeometry.enemySlots`）は変更を要しない。
- 配置は戦闘の開始時に 1 回決め（敵の並び＝index 順に `placeEnemies`）、`BattleScreen` が保持するか、`BattleEntity.layout.cell` に書き込んで渡す。**GameState に中間状態は足さない**（レイアウトは入力から毎回求まる。ADR 0002）。

### 3.8 画面サイズ総当たりの不変条件

`battleLayout.test.ts` の既存の総当たり（幅×高さ×人数）に、グリッド有効時の項目を足す。

- 各敵の占有矩形（板の `pad` を含む）が画面内で、**ログ帯と重なる量が `overlap × 占有領域の高さ` 以下**（#838。許容量 0 のときは従来どおり重ならない）。stage の下端・左右・味方の領域には食い込まない。
- 占有矩形同士が**重ならない**（サイズ混在・配置指定あり含む）。味方の領域とも重ならない。
- ラベルが stage 内、同じ行・隣の占有領域のラベルと重ならない。
- **体数不変**: 同じ群の先頭の敵（`placeEnemies` の結果で固定の位置）について、他の敵の有無（体数 1〜最大）で 1 体目の `x, y, width, size` が変わらない。`cell` は体数を入力に持たないので同一。
- 同じ敵を `1x1` と `2x2` にしたとき、`2x2` の占有領域が `1x1` の 2 倍（同一 `cell` から導出）。
- 奥行き有効時も、縮尺は体数に依らない（最前列の基準がグリッドの最下端固定）。
- `placeEnemies` 単体: 範囲外・重なり・満杯の群をエラーにする、`2x2` + 同列 `1x1` は置けない、first-fit の順序。

実ブラウザ検証（絶対ルール 1）: sit-by-me の敵画像（氷柱・割れたガラス・ビール瓶・釘）で、`battle_enemy_grid` 有効の群を 1 体〜最大で踏み、ライブの A/B 比較で「1 体目が動かない」「窓との重なりが許容量以下」「隣にかぶらない」を確認する。可視判定は computed style で取る。

## 5. 擬似設定の例

frontmatter は共通。

```yaml
battle_layout: side
battle_enemy_grid: 6x2        # 最大 6 列 x 2 行。埋めなくてよい
sprite_style: acrylic
```

敵の定義（サイズ区分は台帳 3-7 から）。

```markdown
[モンスター slime]      名前: スライム        サイズ: 1x1  [/モンスター]
[モンスター icicle]     名前: 氷柱            サイズ: 1x2  [/モンスター]
[モンスター drill]      名前: ドリル          サイズ: 2x1  [/モンスター]
[モンスター bit]        名前: ビット          サイズ: 1x1  倍率: 0.8  [/モンスター]
[モンスター guardian]   名前: ガーディアン    サイズ: 2x2  [/モンスター]
```

### 5.1 普通の群（配置指定なし。従来どおり書いて、サイズだけ効く）

```markdown
[エンカウント率: 1/16]
[エンカウント群: slime, slime+slime, slime+icicle]
```

- 書式は現行と同じ。3 体目までの 1x1 は手前の列（F 列）の上段 → 下段、E 列…の順に埋まる。`slime`（1 体）の位置・大きさは、`slime+slime` のときの 1 体目と**同じ**（R3）。
- `slime+icicle`: 氷柱（1x2）は全行を使うので、スライムが F1 → 氷柱は E 列（E1〜E2）に置かれる。

### 5.2 ボス＋ビット 2 体（配置指定）

```markdown
[エンカウント群: guardian@C1+bit@E1+bit@E2]
```

- ガーディアン（2x2）は C1〜D2 の 4 セル（奥）。ビットは手前の E 列の上下（E1, E2）。
- 描画順: 奥のガーディアン → 手前のビット。ビットを先に倒すとボスだけが残る、という意味づけは #832 系の行動仕様で表し、本設計は位置までを決める。

### 5.3 ランダム構成と重み

```markdown
[エンカウント群: slime*1..3, slime*1..2+drill:2, icicle+slime*0..2:1]
```

- 抽選は 3 群を重み（1 / 2 / 1）で選ぶ。`slime*1..3` は選ばれたあとスライムを 1〜3 体にする。
- 3 つ目は氷柱が必ず 1 体、スライムは 0〜2 体。収まり検証は最大数（氷柱 1x2 + スライム 2）で行う。
- 重みの指定が 1 つでもあれば累積重みで抽選する。1 つも無ければ現行の均等抽選（乱数列も同じ）。

### 5.4 大小混在の 4 体

```markdown
[エンカウント群: drill+icicle+slime+slime]
```

- `drill`（2x1）= 配置は手前の列から: E〜F 列の 1 行目（E1〜F1）。
- `icicle`（1x2）= 全行を使うので、drill の占有する E・F 列には入らず、D 列（D1〜D2）。
- `slime` ×2 = 残りの空き: E2, F2（drill の下）。
- どの体数・どの敵が欠けても、セルの大きさと各敵の位置の基準は同じ。

## 7. 既知のリスク・未確認事項

- **段階 0 の実測（純粋関数・画面 11 幅 × 9 高さ × 敵 1〜6 体 × 縦横比 0.2〜2.5、既定の板パラメータ）**: 窓の下へもぐる量は縦長・正方形（0.2〜1）で枠の高さの約 0.6% 以下（許容量 25% の範囲内で仕様どおり）、横長（1.6 / 2.5）は箱が枠の上へ伸びるため最大 33% / 53% で許容量を超えていた（→ 領域の上端を下げて 25% 以内に収める。横長の敵 1 体で大きさは最大 約 26% 縮む）。2 列で同じ行の板が隣に重なる量は、縦長 0.2 で最大 18px・0.35 で 3px・横長で最大 52px（→ 列ピッチに板を含めて 0）。実ブラウザでの目視は別途。
- #838 の原因は読解による推定。段階 0 の着手時に、sit-by-me の敵画像（氷柱・割れたガラス・ビール瓶・釘）で再現し、窓へもぐる量が許容量 25% を超えるか、`pad` の寄与がどれほどかを実測して確定する。
- 戦闘を起動する経路が `rollEncounter` 以外（イベントからの固定戦闘等）にもある場合、同じ群書式を使うか確認する（段 2 で調査）。
- 正方形セル + 横は中央・縦は下端、は第一案。実機の見た目で、横を右寄せ（味方側）にするほうが自然なら変える（段 4 のライブ比較で決める）。
- 台帳の「ボス = 大型」の区分（2x2 以上）がグリッド 2 行に収まるのは `h ≤ 2` まで。3 行以上の巨体が要るなら `battle_enemy_grid` の行数を増やす（行数の上限 4 で足りるか、実際のボスの寸法で確認する）。
- **ff のポーズ違いの絵（段階 0 の既知のリスク）**: `poseRectOnBase` で基本の絵より大きい slash などへ差し替えると、板はそのポーズの絵ごとに広がるが、配置（列ピッチ・窓との重なり）は基本の絵の縦横比で計算している。ポーズ中だけ隣の板や窓にかぶりうる（演出中の一時的な見た目）。
- **窓との重なりの対象（段階 0）**: `measureWindowOver` が見るのはログ帯だけ。`cross` レイアウトで敵に重なって開く候補窓・手のカーソルとの重なりは対象外。
